# AI 编码纪律触发场景

这份参考文件用于补充说明这个 skill 在什么情况下应该触发，以及触发后重点控制什么。

## 一、最适合触发的场景

### 修 bug

典型表现：

- 用户说“帮我修一下这个问题”
- 用户要求“最小改动解决”
- 已有代码可复现异常或错误行为

重点控制：

- 先复现，再修复
- 不顺手扩大修改范围
- 修完后用同一场景验证

### 小范围改已有代码

典型表现：

- 用户说“改一下这段逻辑”
- 用户明确说“不要动别的地方”
- 只涉及某个方法、某个分支、某个字段处理

重点控制：

- 先明确边界
- 只改与目标直接相关的逻辑
- 不引入额外抽象层

### Debug / 定位问题

典型表现：

- 用户说“帮我看为什么不生效”
- 需要沿调用链定位入口和分支
- 暂时还不确定应该改哪里

重点控制：

- 先定位真实入口
- 明确假设
- 不在没确认根因前就直接改代码

### Code Review

典型表现：

- 用户说“review 一下”
- 需要判断风险、回归和遗漏验证

重点控制：

- 优先指出行为风险
- 检查是否有无关 diff
- 检查是否缺验证闭环

## 二、典型触发话术

- `先分析再改`
- `最小改动`
- `别乱改`
- `不要动无关代码`
- `先列假设`
- `补验证结果`
- `review`
- `debug`

## 三、不适合单独触发的场景

- 单纯问某个 API 怎么用
- 单纯问领域知识
- 单纯问文档内容

这类问题应该优先使用领域 skill。本 skill 只在“执行纪律”同样重要时叠加触发。

## 四、推荐输出模式

### 1. 实现前

先写清：

- 当前理解
- 假设
- 歧义
- 计划如何验证

### 2. 实现中

坚持：

- 最小改动
- 不动无关区域
- 只清理本次改动产生的冗余

### 3. 收尾时

必须说明：

- 实际做了什么
- 跑了什么验证
- 验证结果是什么
- 还有没有残留风险
