# rule-skill Skill 贡献整理

- 提交人：luofuwei
- 日期：2026-04-30
- 关键词：保守编码、最小改动、显式假设、验证标准、范围控制、LLM 工程约束
- 适用范围：需要约束 Codex 的编码行为，降低过度实现、误判需求、范围扩散和无效重构风险时；尤其适用于编码、重构、修 bug、debug、review 这类容易“顺手多做”的任务

## 问题场景

LLM 参与工程任务时，真正高频的问题通常不是“不会写代码”，而是：

- 没澄清假设，直接选了一种解释开始写
- 用户只要一个小改动，却顺手加了配置、抽象和额外功能
- 修一个点，结果把周边代码、注释、格式一起改了
- 最后汇报“已经改好了”，但没有明确的验证闭环

`rule-skill` 的目标不是提高生成速度，而是降低这些典型错误的发生率。它本质上是一组“先收紧行为，再允许编码”的工程纪律。

## 前置条件

- 当前任务属于编码、重构、修 bug、debug 或 code review
- 团队接受“复杂任务上先降速、再换稳定性”的策略
- 希望 Codex 在实现前先说明假设、边界和验证方式
- 希望代码改动保持手术式范围，而不是默认扩散
- 可以接受在发现歧义时先停下来确认，而不是静默选择一种解释

## 解决方案

在动手前先显式写出假设和成功标准；实现时只做最小必要改动；编辑时不碰无关区域；结束时必须拿验证结果闭环，而不是用“应该可以”收尾。

## 关键代码 / API

这个 skill 的核心不是某个具体 API，而是一套固定执行模式。可以把它理解成一个在任何代码任务开始前都能套用的模板。

### 1. 先把模糊目标改写成可验证目标

```java
// 弱目标
"修复这个问题"

// 强目标
1. 先写出复现条件
2. 用测试、日志或稳定复现场景证明问题存在
3. 修改实现
4. 用同一组检查证明问题消失
```

### 2. 先说假设，再决定是否编码

```java
// 进入实现前必须说清楚的内容
// - 我当前理解的问题是什么
// - 我依赖的前提是什么
// - 哪些地方仍有歧义
// - 如果歧义不消除，可能走向哪几种实现
```

### 3. 多步任务必须带验证点

```java
1. 定位调用链 -> verify: 找到真正生效的入口方法
2. 增加最小修复 -> verify: 复现场景输出符合预期
3. 清理本次改动产生的冗余 -> verify: 无新增未使用变量 / import
4. 跑定向验证 -> verify: 目标问题消失，未引入明显回归
```

### 4. 典型的“最小改动”判断标准

```java
// 可以做
- 修复用户明确指出的问题
- 删除本次修改直接造成的无用 import / 变量 / 分支
- 增加完成本次任务所必需的最小测试或校验

// 不应该顺手做
- 改无关模块的命名风格
- 扩展成通用框架或抽象层
- 重排大片代码或统一格式
- 删除原本就存在、但与本次任务无关的旧问题代码
```

## 注意事项 / 常见误区

- 误区 1：把“顺手优化”当成正常行为。这个 skill 明确反对与当前请求无关的扩展、抽象和清理。
- 误区 2：成功标准写成“搞定”“应该可以”“我觉得没问题”，却没有可检查的验证项。
- 误区 3：发现需求有多个解释时，默认挑一个实现。正确做法是先暴露歧义，再决定是否继续。
- 误区 4：为了显得完整，加上用户没要求的容错、配置和抽象层，最后把一个小修复做成重构。
- 误区 5：把“匹配项目已有风格”误解成“可以顺手统一整个文件”。这个 skill 要求只动必要部分。

## 可整理进正式 Skill 的结论

- 对 LLM 来说，先定义假设、边界和验证标准，通常比补更多编码技巧更有效。
- 最小实现和手术式 diff 是控制返工成本的核心，不相关的改动默认都应视为风险。
- 当任务描述不够强时，先把它改写成“步骤 + 验证”的形式，再进入实现，稳定性会明显提升。
